# Платформа быстрых поручений

> **Статус проекта: планирование.** Этот репозиторий задуман как учебный портфолио-проект. README описывает целевой продукт и план реализации; перечисленные возможности пока не следует считать реализованными.

Площадка для небольших локальных поручений, которые нужно выполнить сегодня: забрать заказ из пункта выдачи, выгулять собаку или помочь собрать мебель. Заказчик публикует поручение, исполнитель отправляет запрос, а заказчик одобряет его с инструкциями или отклоняет.

## Цели проекта

- На практике освоить монорепозиторий с несколькими приложениями и общими пакетами.
- Реализовать микрофронтенды на React и понять их независимую сборку и runtime-композицию.
- Изучить NestJS, проектирование API, авторизацию, PostgreSQL и миграции.
- Интегрировать Web Worker, Service Worker и Web Push в работающем пользовательском сценарии.
- Улучшить навык написания тестов React-компонентов, API и сквозных сценариев.
- Изучить всевозможные аспекты продукта от локальной разработки до развернутого контейнера на стенде.

## MVP и пользовательский сценарий

Один аккаунт может и создавать поручения, и откликаться на чужие. Основной сценарий:

1. Заказчик публикует поручение с описанием, районом, временем и указанной наградой.
2. Исполнитель отправляет запрос на выполнение.
3. Заказчик получает уведомление и одобряет запрос с дополнительными инструкциями либо отклоняет его.
4. После одобрения поручение переходит в работу; стороны могут отметить выполнение и завершение.
5. Поручение или запрос можно отменить в соответствии с правилами статусов.

Сервер проверяет права пользователя и допустимость каждого перехода. Если несколько исполнителей запрашивают одно поручение, одобрить можно только одного — изменение должно быть атомарным.

### Не входит в первую версию

- Реальные платежи и переводы денег: награда — только информация в поручении.
- Полноценный чат, сложная геокарта и точная геолокация.
- Отдельная серверная очередь и Redis: для MVP достаточно отправлять push из API.
- Разделение backend на независимо развертываемые микросервисы.

### Почему микрофронтенды, но модульный backend

Фронтенд разделяется на независимо собираемые части, чтобы на практике изучить Module Federation и интеграцию приложений через host-приложение (контейнер). Оно отвечает за общую рамку интерфейса, например навигацию и маршрутизацию, и подключает микрофронтенды. Backend на старте остается модульным монолитом: границы пользователей, поручений, запросов и уведомлений будут явными, но не потребуют преждевременной распределенной инфраструктуры.

## Предлагаемая структура монорепозитория

```text
apps/
  web-host/           # host-приложение (точка входа, навигация, подключение микрофронтендов)
  tasks/              # поручения (информация, каталог, запросы)
  account/            # учетная запись (вход, регистрация, профиль)
  api/                # NestJS API
packages/
  ui/                 # повторно используемые React-компоненты
  contracts/          # общие типы и контракты API
  config/             # разделяемые настройки инструментов, если они понадобятся
```

Это целевая схема, а не требование заранее создавать каждый пакет. Добавлять общие пакеты следует по мере появления реального повторного использования.

## План реализации

### 1. Доменная модель и границы MVP

- Определить поля пользователей, поручений и запросов на выполнение.
- Зафиксировать статусы и допустимые переходы: публикация, запрос, одобрение/отказ, выполнение, завершение и отмена.
- Описать правила доступа и поведение при одновременных запросах.
- Оставить платежи, полноценный чат, карты и серверную очередь за пределами MVP.

**Результат:** согласованная модель продукта, на которой можно строить API и интерфейс.

### 2. Монорепозиторий и общая разработка

- Настроить pnpm workspaces и Turborepo.
- Подготовить TypeScript и единые команды для lint, typecheck, тестов и сборки.
- Определить структуру приложений и пакетов, договориться о правилах общих зависимостей.

**Результат:** приложения и пакеты развиваются в одном репозитории и проверяются согласованными командами.

### 3. API и база данных

- Создать NestJS API как модульный монолит: пользователи, сессии, поручения, запросы и уведомления.
- Описать схему PostgreSQL с Prisma и добавить миграции.
- Добавить валидацию входных данных, единый формат ошибок и серверные проверки бизнес-правил.
- Предусмотреть атомарное одобрение только одного запроса на поручение.

**Результат:** API и база поддерживают основные сущности и правила MVP.

### 4. Cookie-сессии и права доступа

- Реализовать регистрацию, вход и выход.
- Настроить сессионную авторизацию и защищенные маршруты.
- Проверять, что управлять поручением и одобрять отклики может его заказчик.
- Настроить безопасные атрибуты cookie и защиту от CSRF для выбранной схемы.
- Сохранить границу авторизации достаточно изолированной, чтобы позднее сравнить или заменить ее на JWT.

**Результат:** два пользователя могут безопасно работать с поручениями в браузере.

### 5. Host-приложение (контейнер) и микрофронтенды

- Создать React + TypeScript приложения на Vite.
- Реализовать host-приложение (контейнер), подключающее микрофронтенды через Vite Module Federation.
- Начать с двух областей: каталог/создание поручений и личный кабинет/запросы.
- Добавить общий UI-пакет и пакет контрактов только там, где есть конкретное повторное использование.

**Результат:** независимо собираемые части интерфейса работают как одно приложение.

### 6. Сквозной сценарий поручения

- Реализовать публикацию и просмотр поручений.
- Добавить отправку запроса, одобрение с инструкциями и отказ.
- Реализовать выполнение, завершение и отмену.
- Синхронизировать статусы между API и интерфейсом; корректно обрабатывать ошибочные и повторные действия.

**Результат:** основной пользовательский сценарий проходит от публикации до завершения.

### 7. Web Worker, Service Worker и Web Push

- Использовать Web Worker для отдельной от UI-потока работы с каталогом, например ранжирования или фильтрации.
- Настроить Service Worker для app-shell-кэша и обработки push-событий.
- Отправлять Web Push при новом запросе заказчику и при решении по запросу исполнителю.
- Обработать отказ пользователя от разрешения, неподдерживаемые браузеры и локальные VAPID-ключи.
- Не помещать чувствительные инструкции или персональные данные в push-payload.

**Результат:** фоновые возможности привязаны к реальным событиям приложения, а не существуют только как демонстрационный пример.

### 8. Автоматические тесты

- Настроить Vitest и React Testing Library для поведения и состояний React-компонентов.
- Покрыть тестами API авторизацию, права доступа, статусы и одобрение запросов.
- Добавить Playwright E2E для полного сценария заказчик–исполнитель.
- Проверить конкурирующие запросы, недопустимые переходы и обработку отказа в push-разрешении.

**Результат:** важные правила проверяются автоматически на уровне компонентов, API и пользовательского сценария.

### 9. Docker и воспроизводимый запуск

- Сначала поднять PostgreSQL локально через Docker Compose.
- Затем добавить multi-stage Dockerfile для API и нужных web-приложений.
- Настроить Compose для локального запуска всего проекта и применения миграций.
- Документировать переменные окружения, секреты, порты и настройку Web Push.

**Результат:** проект можно запустить локально по инструкции без ручной установки PostgreSQL.

### 10. CI и портфолио

- Настроить CI для установки зависимостей, lint, typecheck, тестов и сборки.
- Дополнить README архитектурой, инструкцией запуска, основными сценариями и известными ограничениями.
- Кратко зафиксировать ключевые решения: Module Federation, модульный монолит и cookie-сессии/JWT.
- Проверить запуск проекта с нуля по документации.

**Результат:** репозиторий наглядно демонстрирует проект и дает воспроизводимый способ его проверить.

### 11. Учебная итерация по JWT

- После работающего MVP провести отдельную итерацию: заменить сессионную авторизацию на JWT или сделать изолированное сравнение.
- Разобрать хранение и передачу токенов, обновление и отзыв, а также браузерные риски.
- Повторно выполнить тесты прав доступа и API-контрактов.

**Результат:** практическое понимание trade-off между cookie-сессиями и JWT без поддержки двух механизмов одновременно в первой версии продукта.

## Принципы и критерии готовности

- Сначала законченный сквозной сценарий, затем дополнительные технологии и расширения.
- Состояние и права проверяются сервером, а не только скрытием кнопок во фронтенде.
- Каждый этап должен оставлять проект запускаемым и пригодным для проверки.
- MVP считается демонстрируемым, когда два пользователя могут пройти сценарий поручения, автоматические проверки проходят, а локальный запуск описан и воспроизводим.
